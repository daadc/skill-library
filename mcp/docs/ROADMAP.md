# Knowledge Connection MCP 路线图

## 当前结论

当前交付是一个 **可运行、已验证的核心 MCP 服务 MVP**，而不是完整的开发者产品。它已有一个名为 `knowledge-connection-mcp` 的命令行**启动入口**，可接受 `--root` 并以 stdio 运行 MCP 服务；但它尚不是可供人直接执行 `index`、`search`、`node`、`graph` 或 `context` 的交互式 CLI。当前包中也没有 HTML、React、CSS 或 `package.json` 资源，因此 **前端界面尚未实现**。

> 推荐顺序是：先将真实检索任务做成可脚本化、可评测、可调试的 CLI 和持久化索引能力；在有明确的人工浏览、知识治理或可视化诊断需求后，再建设可选的本地前端。MCP 是当前 AI Agent 的主路径，CLI 是最低成本的可观测与运维面，前端不应抢在检索质量与索引生命周期之前。

## 现有能力与缺口

| 能力层 | 当前状态 | 已具备能力 | 关键缺口 |
|---|---|---|---|
| 核心索引 | 已实现 | Markdown/YAML 知识节点、Python AST 符号、引用/包含/导入/静态调用/词项关系。 | 无增量索引、无持久化、无 Tree-sitter 多语言 adapter。 |
| MCP 服务 | 已实现 | 五个只读工具、stdio、输入边界、根目录限制、结构化结果。 | 无索引状态、刷新、评测或诊断工具。 |
| 检索 | 已实现 | 确定性字段权重、知识优先、节点详情、邻域探索、受预算上下文包。 | 无 BM25/全文索引、同义词、语义召回、重排、反馈闭环或基准集。 |
| 命令行 | 仅启动器 | `knowledge-connection-mcp --root <path>` 启动 MCP。 | 无人机交互/脚本 CLI、无 JSON 输出模式、无配置、无 shell completion。 |
| 前端 | 未实现 | 无。 | 无搜索工作台、节点详情、图谱浏览、索引进度、质量/来源治理视图。 |
| 交付治理 | 初步实现 | ADR、交互契约、证据审校、测试与验证报告。 | 无版本化发布、变更日志、迁移策略、性能基线和目标客户端兼容矩阵。 |

## 北极星结果与护栏

该产品的目标不是“画一个图”，而是让 AI 或开发者在可控的上下文预算下，找到 **足以支持下一步决策的、带来源和定位的知识及实现线索**。后续阶段应围绕首次命中质量、证据完整性、调用轮次、索引新鲜度和资源成本衡量，而不是按工具数量或节点数量衡量。

| 指标 | 定义 | 护栏 |
|---|---|---|
| 首次有用命中率 | 代表性查询的前 3 条是否含可直接使用的知识节点或精确符号。 | 结果必须显示路径、行号和关系理由。 |
| 证据完整率 | 上下文包中有来源、前提、风险或验证字段的知识节点比例。 | 不以词项关联代替引用证据。 |
| 任务成本 | 完成一个检索任务的工具调用数、上下文字符数和索引耗时。 | 不通过无界全文或后台扫描来换取表面召回。 |
| 索引新鲜度 | 索引快照与工作树变化的差异。 | 刷新必须显式、可观察、可回退。 |
| 安全边界 | 根目录外读取、写入、执行、网络访问的违规次数。 | 必须保持为零。 |

## Phase 0：将 MCP MVP 变成可调试的开发者工具

此阶段优先实现真正的 CLI，而不改变 MCP 只读安全模型。CLI 的每个查询命令在进程内构建或加载一个快照，并可选以 JSON 返回，便于 shell、CI 和 Agent 评测调用。

| 交付项 | 主要内容 | 验收条件 |
|---|---|---|
| `knowledge-connection serve` | 取代当前仅有的启动入口；支持 `--root`、日志级别与受限配置文件。 | stdio MCP 行为与当前兼容。 |
| `knowledge-connection index` | 输出文件、节点、边、跳过原因、耗时与格式统计。 | 能对当前仓库重复运行；可输出人读表格和 JSON。 |
| `search`、`node`、`connections`、`context` 子命令 | 覆盖五个 MCP 查询的同等只读能力。 | CLI 与 MCP 在相同输入下返回同一快照的同类结果。 |
| 配置与忽略规则 | 支持仓库内显式配置、扩展名/目录白名单、文件大小与预算限制。 | 默认安全；配置不会扩大允许根目录。 |
| 离线评测集 | 将真实查询、预期路径/节点、错误案例写入版本控制。 | 每次变更输出首条/前 3 命中、上下文预算与回归差异。 |

该阶段完成后，维护者可以无需 MCP 客户端就复现索引、调试排序、制作 CI 回归基线。其风险最低，且能为前端提供稳定的数据契约。

## Phase 1：检索质量与索引生命周期

此阶段的目标是让索引可持续、检索可评估。先保留当前确定性召回作为基线，然后以评测结果决定是否引入更复杂组件；不要先引入嵌入模型再寻找问题。

| 交付项 | 主要内容 | 决策门槛 |
|---|---|---|
| 持久化图存储 | SQLite 存放节点、边、文件哈希、索引版本和构建元数据；读写仍限制在服务专用目录。 | 当前仓库或真实目标仓库的全量重建成本已影响工作流。 |
| 增量刷新 | 基于内容哈希的文件级重建、删除检测、原子快照切换。 | 必须证明与全量重建结果一致，并有故障回退。 |
| 结构化字段抽取 | 识别知识卡的原则、前提、风险、验证、非目标、来源和 review trigger。 | 字段缺失可降级，不能把普通文本误报为已验证证据。 |
| 多语言 parser adapter | 先采用 Tree-sitter adapter，再按真实仓库语言需求支持 TypeScript/Java/Go 等。 | 每种语言须有夹具、符号/调用边界说明与回归测试。 |
| 混合检索 | 先加入 BM25/字段全文索引；只有评测显示语义召回缺口时才增加本地嵌入或可选远端模型。 | 评测集的首次有用命中率显著改善，同时不损害可追溯性和预算。 |
| 排序与解释 | 把结果分解为字段匹配、图距离、来源强度、时间/版本状态等可见信号。 | 任何排序变化可解释、可复现并可回归测试。 |

## Phase 2：可选的本地知识工作台前端

前端应定位为 **人工审阅、调试与治理界面**，而不是 MCP 的必需依赖。建议在 Phase 1 的持久化与 CLI 契约稳定后，创建本地绑定 `127.0.0.1` 的工作台，并复用同一只读查询 API。任何监听端口、认证或远程访问策略都应在实施前单独形成 ADR。

| 界面能力 | 用户任务 | 依赖与验收 |
|---|---|---|
| 搜索工作台 | 输入主题/符号，比较知识、来源、场景和代码命中。 | 调用与 CLI/MCP 一致的查询层；结果展示评分原因、路径和行号。 |
| 节点详情 | 阅读知识卡字段、源码片段、来源和直接关系。 | 词项关联须显式标为弱关联；引用应可定位。 |
| 关系浏览 | 从知识原则探索到场景、来源和代码符号。 | 默认局部、深度受限，避免无界关系图。 |
| 索引与质量面板 | 查看索引版本、覆盖语言、跳过文件、解析失败、评测趋势与陈旧知识。 | 无后台隐式刷新；能导出安全化诊断。 |
| 治理工作流 | 标记节点的 owner、审核日期、review trigger 和弃用状态。 | 写操作必须采用显式审批、审计记录与回退策略，不能复用当前只读权限。 |

UI 技术选型不在当前承诺范围内。若实施，优先选用轻量本地静态前端加同进程/本地 API；只有出现多人协作、远程访问或权限模型需求时，才评估完整 Web 服务与认证。

## Phase 3：团队协作与运行治理

当工具被多个仓库、多个 Agent 或多人使用时，再推进共享能力。此阶段会引入实际的权限、数据和发布影响，属于高于当前 R1 的变更，必须由用户/维护者进行架构、安全与发布审批。

| 方向 | 可能能力 | 强制门禁 |
|---|---|---|
| 可移植索引产物 | 可选导出/导入、版本签名、schema migration。 | 完整性校验、来源/隐私审查、回退和兼容策略。 |
| 团队知识治理 | owner、审核任务、陈旧性提醒、变更触发。 | 角色/权限模型、审计日志和人工批准。 |
| 发布工程 | 版本化打包、锁文件、SBOM、变更日志、目标客户端兼容验证。 | 可复现构建、依赖审查、发布/回滚 runbook。 |
| Agent 评测 | 任务集、工具选择准确性、引用可靠性、成本/延迟预算、停止/交接行为。 | 评测集与提示分离，失败样本可复现。 |

## 建议的下一步切片

建议下一次只实施 **Phase 0 的 CLI + 离线评测集**。它能立即回答“索引是否新鲜、为什么这条结果排第一、改动是否使检索变差”，也会为后续 UI 提供稳定接口。完成这一切片后，再以真实使用记录决定优先建设 Phase 1 的持久化/增量索引，还是 Phase 2 的人工工作台。

> 前端是明确的后续能力，不是遗漏的 bug；当前实现有意先完成被 AI 调用的最小只读核心。CLI 则是当前最应补齐的开发者体验与可观测性层。

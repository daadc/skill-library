# 并发与韧性工程知识卡

> **韧性不是“多加几个中间件”。** 它是一组按请求路径、资源上限、业务优先级和恢复行为共同设计的契约。错误的重试、超时或队列通常会放大故障。

## KC-RES-001：先做端到端请求预算，再配置单点超时

**问题。** 为什么“每个 HTTP/RPC 都设 30 秒超时”会导致长尾、线程耗尽与级联故障？

**原则。** 每个跨进程远程调用应有连接和请求超时；超时不是孤立常量，而是用户/上游 deadline 在调用链上的预算分配。等待过久会占用线程、连接、内存和端口；设置过短又会制造误超时与重试流量。[1] [2]

```yaml
request_budget:
  client_deadline_ms: 800
  gateway_reserve_ms: 80
  service_compute_budget_ms: 180
  downstream_budget_ms: 400
  retry_reserve_ms: 100
  cancellation: "deadline/cancellation 向下游传播"
  unknowns: ["网络抖动", "冷启动", "TLS/DNS 覆盖范围", "排队时间"]
```

**设计步骤。**

1. 从用户体验或上游 SLA 定义总 deadline，而不是从客户端库默认值开始。
2. 把网关、排队、服务处理、下游、重试和安全余量纳入预算；子调用不能无限大于父预算。
3. 用下游真实延迟分位数、可接受误超时率和网络范围提出初始假设；测试 DNS、TLS、连接复用和冷启动是否被计入。
4. 把 cancellation/deadline 向下游传播，在工作已无价值时尽早停止。
5. 按依赖、端点、版本和错误类型观测超时、排队、in-flight、连接池耗尽与取消率。

**反模式。** 全局固定超时；只设置 socket read timeout；忽略握手/DNS；下游超时大于上游截止；超时后不取消后台工作。

## KC-RES-002：重试、退避与抖动怎样才不会把故障放大？

**问题。** 临时失败时，怎样提高成功率又不制造 retry storm？

**原则。** 重试是向下游索取额外资源的行为。仅对可能成功、幂等或有幂等键的操作重试；优先在调用链的一个层级实施重试；限制次数，使用封顶指数退避和抖动，并对重试流量设置独立预算/令牌桶。[1] [2]

| 判断 | 合理起点 | 不能默认重试的情况 |
|---|---|---|
| 操作语义 | 只读、幂等写或带稳定 idempotency key | 创建/扣款/发货等未知是否已生效的副作用 |
| 失败类型 | 明确瞬态错误、短暂网络/容量异常 | 参数、权限、业务校验、确定性 4xx |
| 层级 | 选一个最能理解业务成本的层 | 每层各自重试，形成乘数放大 |
| 频率 | 封顶指数退避 + 抖动 + 总 deadline | 立即、同步、无限或定时齐步重试 |
| 容量 | 重试令牌/预算、按优先级丢弃 | 与正常流量共享无限连接/线程/队列 |

**关键边界。** 即使连接失败或超时，也不能证明服务端没有执行副作用。为写操作设计稳定的请求 ID、去重记录或业务唯一约束；重试策略必须与持久化语义一起验证。[2]

## KC-RES-003：熔断器如何正确地与超时、重试和降级协作？

**问题。** 什么时候应该熔断，而不是再试一次？

**原则。** 熔断器用于暂时阻止很可能持续失败的远程操作，让依赖恢复并使调用方快速失败；它不同于期待瞬态成功的重试。典型状态是 Closed、Open 与 Half-Open，恢复探测应限制流量，不能把恢复中的依赖再次冲垮。[3]

```yaml
circuit_contract:
  dependency_and_operation: "按依赖/操作/分片或租户定义，避免误伤独立资源"
  failure_window: "错误、超时、过载信号的时间窗口和分类"
  open_policy: "阈值、最短打开时间、fallback/用户提示"
  half_open: "有限探测并发、成功/失败转移规则"
  observability: "状态转换、拒绝数、探测结果、fallback 质量、关联 trace"
  manual_controls: "安全的强制打开/关闭、审计和过期机制"
```

**何时不用。** 只有可靠的幂等重试已足够、事件驱动队列已有隔离/重试机制、调用是本地内存操作，或熔断恢复等待无法接受时，不应机械加入熔断器。[3]

**验证。** 在依赖慢、返回 429/503、完全不可用、部分分片故障和恢复抖动下，测试状态转换、fall back、告警、人工覆盖与恢复探测。

## KC-RES-004：如何用舱壁、限流和队列控制并发？

**问题。** 为什么共享线程池、连接池或无界队列会让单一依赖拖垮整个服务？

**原则。** 舱壁模式把资源隔离成独立池/队列/实例/单元，使一个依赖、租户或业务优先级的异常不耗尽其他路径的资源。队列会消耗内存并增加延迟；长期超出处理能力时应尽早拒绝、限流或降级，而不是用大队列隐藏过载。[1] [4]

| 隔离对象 | 实现示例 | 需测量的代价 |
|---|---|---|
| 下游依赖 | 独立连接池、线程池、并发 semaphore、请求队列 | 空闲浪费、池大小、排队、饥饿 |
| 关键业务路径 | 高低优先级队列、独立 worker、QoS | 公平性、优先级反转、降级体验 |
| 租户/客户 | 每租户配额、cell、分片、限流键 | 热点、公平、隔离成本、数据边界 |
| 集群/服务 | K8s 资源 requests/limits、HPA、独立 namespace/节点池 | 资源碎片、扩容速度、故障域 |

**容量公式的使用边界。** Little 定律可帮助把稳定系统的平均并发近似理解为到达率 × 平均处理时间，但它不是超载时设置无限队列的理由。应通过压测找出服务的饱和点和早拒绝策略，而非仅靠平均指标。

## KC-RES-005：优雅降级和故障恢复需要产品契约

**问题。** 依赖不可用时，“返回缓存”或“少显示一点内容”何时是可接受的？

**原则。** 负载丢弃用于保护系统不崩溃；优雅降级进一步减少工作量或提供较低质量结果。两者都必须由业务声明正确性边界、用户提示、可观测性和恢复条件，且应定期演练，否则极少运行的降级路径最可能在事故中失效。[1]

| 能力 | 可能降级 | 禁止无声降级的例子 |
|---|---|---|
| 搜索/推荐 | 缓存、较少候选、延迟刷新 | 把过期结果标成实时库存或价格 |
| 读取列表 | 最近快照、部分结果、稍后刷新 | 结算、权限、余额、风控决定 |
| 写入操作 | 排队、明确“处理中”、可幂等重试 | 隐瞒写入是否成功或重复执行 |
| 后台任务 | 降低并发、延后、暂停低优先级 | 丢失不可重建的业务事件 |

**恢复门。** 降级开关、默认值、缓存 TTL、回放和重新启用必须可审计；恢复后验证数据校正、积压清理、用户通知和 SLO 回归。

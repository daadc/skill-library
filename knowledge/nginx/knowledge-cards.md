# Nginx 知识卡

## KC-NGX-001：如何定义安全的反向代理契约？

**问题。** 将 Nginx 放在应用服务前面时，哪些行为必须显式配置和测试？

**原则。** `proxy_pass` 只是请求转发起点。生产代理契约必须明确 URL 重写、`Host`/客户端地址链、协议升级、超时、请求与响应缓冲、上游 TLS、重试条件、错误页和日志字段；默认行为不等于业务语义。[1]

| 维度 | 必须回答的问题 | 验证方式 |
|---|---|---|
| 请求目标 | URI 是否重写？查询参数与编码是否保留？ | 契约测试与访问日志 |
| 身份/来源 | 哪些 `X-Forwarded-*` 头可信？上游如何识别真实客户端？ | 伪造请求头与多层代理测试 |
| 超时 | 连接、发送、读取和客户端超时分别服务于什么故障边界？ | 注入慢连接、慢响应和上游不可达 |
| 缓冲/流式 | 是否允许磁盘临时文件？SSE/下载/大响应需要何种语义？ | 大响应、慢客户端、流式响应压测 |
| 重试 | 哪些请求可安全重试？如何避免重复写？ | 幂等/非幂等请求故障注入 |

**风险。** 启用缓冲时，Nginx 可将代理响应存入内存或临时文件；关闭缓冲时，代理读取上游与向客户端传输更同步。二者影响内存、磁盘、尾延迟和流式行为，不能凭“性能优化”标签盲选。[1]

## KC-NGX-002：如何选择上游负载均衡策略？

**问题。** round-robin、`least_conn`、`ip_hash` 和权重的取舍应如何做？

**原则。** 不指定算法时，上游通常采用 round-robin。请求处理时长差异显著时，`least_conn` 可能减少忙实例继续接收请求的概率；`ip_hash` 提供以客户端 IP 为键的粘性尝试，但不应被用来掩盖服务端会话状态设计问题。[2]

**决策步骤。**

1. 测量请求时长、连接寿命、实例差异、会话状态与客户端 NAT 情况。
2. 无会话、负载相近时，先以 round-robin 为基线。
3. 长连接或请求时长差异明显时，比较 `least_conn` 与应用层并发/队列指标。
4. 只有确实需要短期粘性且能接受 NAT 倾斜/节点故障变化时，评估 `ip_hash`；优先把会话放入共享存储或签名令牌。
5. 用权重反映经过验证的容量差异，不要用它长期掩盖异常节点。

**风险与验证。** OSS Nginx 的默认健康判断是基于实际请求失败的被动行为；负载算法、失败阈值、重试与应用幂等性必须一起压测。发布时观察每实例 QPS、并发连接、错误、P99 和重试，避免只看平均值。[2]

## KC-NGX-003：如何上线限流而不误伤用户？

**问题。** 如何把 `limit_req`/`limit_conn` 变成可观测的保护措施，而非不透明的 503 来源？

**原则。** 限流需要先选择可信且公平的键。以 IP 为键在 NAT、办公网络和代理链下可能误伤多个用户；`burst`、`delay` 和 `nodelay` 会改变超额请求被延迟还是拒绝的体验。应先使用 dry-run 收集影响，再按端点和身份风险逐步启用。[3]

**上线契约。**

```yaml
rate_limit_contract:
  protected_route: "明确的高成本或高风险端点"
  key: "经审查的用户/租户/API key/可信来源组合"
  baseline: "真实峰值、突发和正常失败率"
  behavior: "rate、burst、delay/nodelay 与预期状态码"
  observability: "限流命中、排队延迟、拒绝率、按键分布、上游饱和度"
  rollout: "dry-run → 小流量 → 逐步扩大"
  exception_path: "可信内部调用、管理操作和申诉/恢复路径"
```

**验证。** 以单用户突发、共享 NAT、恶意流量、重试客户端、上游降级和多个 Nginx 实例为场景测试；确认客户端能区分可重试、被拒绝与业务错误。

# Kafka 知识卡

## KC-KFK-001：主题、分区与键应如何服务业务顺序和扩展性？

**问题。** 如何避免只按业务名建 topic，却没有定义顺序、分区键、保留与消费者并发语义？

**原则。** Kafka 将事件组织在 topic 中，并将 topic 分为 partitions。具有相同键的事件会写到同一分区；对一个给定 topic-partition 的消费者，Kafka 保证按写入顺序读取该分区的事件。因此“全局顺序”不是默认保证，分区键就是顺序、并发、热点和重放边界的一部分。[1]

**主题设计卡。**

```yaml
topic_contract:
  purpose: "事件为何存在，谁是权威生产者"
  event_key: "保证何种实体粒度顺序；为空时的影响"
  partitions: "初始并发、未来扩展、键分布假设"
  retention: "时间/容量、重放窗口、合规删除要求"
  replication: "可用性与成本目标"
  consumers: "消费组、最大并行度、重试/DLQ/回放责任"
  schema: "兼容策略、演进所有者、敏感字段约束"
  observability: "吞吐、lag、错误、重试、DLQ、磁盘、复制健康"
```

**验证。** 使用真实或模拟的键分布测试热点、消费者并发、扩容、重放、乱序输入和重复事件；用业务不变量验证，而不是仅观察 consumer lag。

## KC-KFK-002：如何设计“至少一次”处理的幂等与重试？

**问题。** 如何避免把 Kafka 能力误解为端到端业务“恰好一次”？

**原则。** Kafka 提供多种保证和 API，但端到端结果还取决于生产者、消费者、外部数据库、HTTP 调用、偏移提交和失败恢复。应先定义业务效果的去重键、幂等写入、原子边界、重试策略、死信/人工修复和可重放性，再讨论具体客户端参数。[1] [2]

| 故障点 | 需要的设计 |
|---|---|
| 生产端重试 | 稳定事件 ID、幂等生产与顺序/吞吐取舍、可审计错误处理 |
| 消费端崩溃 | 明确偏移提交与业务副作用的先后；可重复执行的处理器 |
| 外部写入 | 唯一约束、幂等 key、outbox/事务边界或补偿机制 |
| 毒消息 | 限次重试、可观察的失败原因、DLQ/隔离、人工回放流程 |
| 回放 | 版本兼容、数据权限、下游幂等、容量和成本预算 |

**验证。** 注入重复、重排、消费者重启、偏移提交失败、外部依赖超时和部分成功；检查最终业务状态、审计记录与可恢复性。

## KC-KFK-003：如何管理事件契约与数据生命周期？

**问题。** 多团队共享 Kafka 后，如何避免字段悄悄改变、敏感数据长期留存、消费者无法升级？

**原则。** Kafka topic 可有多个生产者和消费者，事件保留由 topic 配置控制，消费后不会自动删除。事件结构、兼容性、保留、访问控制和删除要求必须成为团队之间明确的产品/数据契约。[1]

**发布门。**

1. 为每个事件定义业务名称、所有者、schema、版本、必选/可选字段、默认值和兼容策略。
2. 禁止无治理的字段重命名、语义改写、敏感字段扩散和无限保留；涉及个人/机密数据时先通过安全与合规审查。
3. 生产者变更先验证旧消费者，消费者变更先验证旧事件；保留可追踪的兼容测试样本。
4. 明确 topic 权限、生产/消费审计、保留与删除策略、数据导出路径和 incident runbook。
5. 由 `product-discovery-manager` 确认业务语义，由 `data-engineer` 确认生命周期，由 `quality-engineer` 维护兼容/回放场景。

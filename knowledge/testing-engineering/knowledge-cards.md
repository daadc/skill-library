# 测试工程知识卡

## KC-TEST-001：按风险与失效模式分配测试，而不是背诵金字塔

小测试通常快、可靠且易于在开发/提交阶段运行；较大测试能覆盖配置、真实依赖、负载、跨进程/机器、用户流程和涌现行为，但会带来成本、非确定性、所有权和维护问题。[1]

| 风险/问题 | 最小优先测试 | 必要时补充 |
|---|---|---|
| 领域规则、纯函数、边界输入 | 单元/属性测试 | 代码审查、变异/边界测试 |
| 服务与数据库/缓存交互 | 真实 DB 或高保真 fake 的集成测试 | 迁移/锁/事务/恢复测试 |
| API/事件兼容性 | schema/contract 测试、producer-consumer 测试 | 混合版本、回放/重试/乱序测试 |
| 用户关键旅程 | 最少量高价值 E2E | 可访问性、跨浏览器、灰度合成探测 |
| 容量/韧性 | 负载、延迟、故障注入、恢复测试 | staging/演练、生产受控实验 |
| 配置/部署 | IaC/config schema/策略测试 | 预发部署、回滚/恢复演练 |

**选择准则。** 首先问“什么失效模式会让用户、数据、安全或成本受损”，然后选可在合理时间内提供足够信心的最小测试。不要用 E2E 覆盖所有逻辑，也不要只因 unit test 通过就假设部署、配置、依赖和用户工作流正确。

## KC-TEST-002：fidelity 与 hermeticity 是权衡，不是单一分数

**fidelity（真实度）** 表示测试是否反映真实系统行为；**hermeticity（隔离度）** 表示是否不受其他测试、用户状态、共享基础设施和不受控依赖影响。高真实度常增加成本/脆弱性，高隔离度可能掩盖真实集成问题。[1]

**实践。** 将配置/依赖版本化；优先使用由依赖 owner 提供并维护的 fake；为关键路径设置少量可复现的高保真集成测试；共享预发和生产验证只作为风险证据的一部分，而不是取代提交前阻断；为跨团队大测试明确 owner、数据、环境、预算和失败诊断路径。

## KC-TEST-003：契约测试保护边界，不能替代行为验证

OpenAPI 等机器可读规范可支持文档、代码生成和测试，但它们不能完整表达业务状态、权限、幂等、异步交付、兼容性和错误恢复。[2]

**最小契约验证。** schema 校验、向后兼容 diff、producer 示例、consumer 关键假设、稳定错误/权限语义、版本/弃用规则。对于事件还要验证 key、顺序、重复、延迟、重放、DLQ 和 handler 幂等。

**反模式。** 只有 schema snapshot；mock 与真实服务各自演化；消费者不参与；把 HTTP 200 当业务成功；忽略混合版本和部署顺序。

## KC-TEST-004：回归选择应以变更影响和用户风险为依据

每个 PR 不必全量执行所有慢测，但也不能只运行作者选中的快测。建立从代码/配置/schema/依赖/数据迁移到测试组、契约消费者、SLO 和 Runbook 的映射；安全、权限、共享库、生成制品、迁移和关键路径扩大回归范围。

| 信号 | 回归升级动作 |
|---|---|
| API/event schema 修改 | 契约/兼容/消费者测试 |
| DB migration/ORM 行为修改 | migration、对账、锁/事务、恢复、性能测试 |
| auth/permission 修改 | 负面授权、跨租户、审计、安全审查 |
| 并发/队列/重试修改 | 故障注入、重复/乱序、资源上限、恢复 |
| 容器/部署/配置修改 | 镜像、配置、policy、预发/合成探测、回滚验证 |

## KC-TEST-005：质量通过不是“测试绿”，而是风险证据足够

测试结果必须连接到用户目标和可观测结果。SLI/SLO 和错误预算可为发布/回归取舍提供共同语言，但目标必须从用户在意的结果倒推，并明确度量范围、窗口和有效条件。[3]

**发布前质量摘要。** 已知风险、未覆盖风险、测试层与结果、数据/环境差异、性能/韧性证据、契约/安全结果、SLO 影响假设、灰度范围、停止/回退阈值、post-release 观察 owner。未知或未测试的风险不能被“总体通过”掩盖。

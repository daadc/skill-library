# 可观测性与性能知识卡

## KC-OBS-001：从用户结果建立遥测，不从“能采什么”开始

OpenTelemetry 将 traces、metrics、logs、baggage 和 profiles 作为互补信号：trace 表示请求路径，metric 是运行时测量，log 是事件记录，baggage 是跨信号上下文，profile 记录代码级资源使用。[1]

**设计顺序。** 用户任务/业务结果 → 失败/延迟/正确性风险 → SLI/SLO → 必需信号与属性 → dashboard/alert/runbook → 存储/采样/隐私成本。每个信号要有 owner、字段语义、敏感性、保留期、基数上限、采样策略和使用者。

**关联准则。** 跨层关联用稳定 request/trace/operation/correlation ID；不要把 email、token、原始 payload 或无限制用户 ID 直接写进高基数 metric label 或可广泛访问日志。

## KC-OBS-002：SLO 是产品与工程的共同约束

SLI 是经定义的质量测量，SLO 是目标，SLA 是含明确后果的约定。应从用户关心的行为倒推指标，明确范围、窗口、成功定义和排除项；延迟通常应看分布/分位数而非单一平均值。[2]

| 服务类型 | 常见用户结果信号 | 不要漏掉 |
|---|---|---|
| 同步 API | 成功率、端到端延迟、正确性、吞吐 | 客户端视角、错误延迟、租户/操作类别 |
| 异步任务/事件流 | 完成率、端到端延迟、积压、重复/失败、数据正确性 | DLQ、重放、最新/最旧消息年龄 |
| 存储/数据 | 可用性、读写延迟、持久性、正确性 | 恢复目标、复制/备份、对账 |
| 用户体验 | 页面/关键动作完成、交互延迟、失败恢复 | 前端错误、网络/地域/版本差异 |

**错误预算。** 允许在目标下管理可靠性与发布速度的权衡，但不是自动发布许可证。预算消耗、事故影响、变更风险和未验证假设必须进入发布决策。

## KC-OBS-003：告警应指向可行动的用户影响

Google SRE 区分 black-box（用户可见症状）与 white-box（内部状态/原因/预警）。两者互补：前者避免只盯内部指标，后者支持定位和提前发现。[3]

**Pager 门槛。** 告警应紧急、可行动、现实或迫近用户影响、具备 owner/Runbook，并且不与其他 alert 重复。不能回答“谁现在可以安全地做什么”时，创建 ticket/趋势看板而不是 page。

**四类基础信号。** latency、traffic、errors、saturation 是用户服务的起点，不是全部。每类需按服务/租户/操作的重要性评估，区分成功/失败延迟、显式/隐式业务错误和资源瓶颈。[3]

## KC-OBS-004：性能结论必须来自可复现实验

性能不是“压测 QPS 数字”，而是给定 workload、数据、硬件/容器资源、依赖、配置、并发、预热、版本、指标、运行时长和失败条件下的结果。负载/大测试可以揭示小测试难覆盖的排队、配置、依赖、饱和与涌现问题，但更贵、更慢且更容易受到环境影响。[4]

**实验契约。**

| 字段 | 最低要求 |
|---|---|
| 假设 | 具体改动将改善/不会破坏哪个用户或系统结果 |
| Workload | 操作比例、payload、并发/速率、突发、数据分布、冷/热状态 |
| 环境 | 版本、资源、拓扑、依赖、隔离度与与生产差异 |
| 指标 | SLI、p50/p95/p99、错误、饱和、队列、成本/资源、正确性 |
| 比较 | 基线、候选、相同条件、统计/重复与异常解释 |
| 停止条件 | 错误/数据风险/资源安全阈值、人工升级 |
| 结论 | 可迁移范围、限制、后续验证和对发布的影响 |

## KC-OBS-005：可观测性是发布、重构和 AI 团队的验证层

每项 R1+ 变更应能说明：要观察的用户/业务/技术信号，dashboard/traces/logs 的位置，异常归属/升级，观察窗口，停止/回退条件，和 post-release 复核。对 AI 生成的设计或代码，遥测是检验假设的工具；模型的自评、静态检查或测试绿灯都不能替代上线后的用户和运行信号。

# 可观测性与性能场景卡

## SC-OBS-001：Go 服务发布后成功率正常但用户投诉变慢

**输入。** 新版本已灰度，5xx 未明显增加，但高价值客户反馈“提交订单很慢”。

**检查路径。** 先从用户操作/租户/区域的端到端延迟 SLI 确认范围；按成功/失败区分 p50/p95/p99；以 trace 查看 API、DB、Redis、Kafka/worker、外部支付和队列等待；以 metrics 检查流量、错误、连接池/CPU/内存/队列/DB 饱和；用结构化 logs 验证特定错误和重试，但不暴露用户敏感数据。

**决策。** 若影响达到发布契约的停止条件，暂停/回退或缩小灰度；若只看平均值或服务器 CPU 就宣布“无问题”，证据不足。最终更新 dashboard、告警、Runbook 与性能假设。

## SC-OBS-002：Kafka 消费堆积与重复处理

**输入。** 发布后消费者消费变慢，lag 上升，重试使同一业务事件出现多次。

**必需信号。** 按 topic/partition/consumer group 的吞吐、lag、最旧消息年龄、处理延迟、成功/失败/DLQ、重试次数、外部依赖延迟/错误；trace/correlation ID 连接生产、消费、DB 写入和副作用；业务对账指标确认是否漏单/重复/顺序破坏。

**停止与恢复。** 明确暂停/扩容/限流/回退/DLQ/重放的授权和数据边界。恢复成功的标准是 backlog 消化、错误预算稳定、对账通过而非“lag 归零”单一条件。

## SC-OBS-003：容量评审与压测结论

**输入。** 计划做营销活动，预计峰值是日常的 8 倍。

**实验要求。** 产品和数据团队提供真实的操作比例和数据形态；SRE/后端定义速率、突发、并发、预热、资源、依赖降级情境；质量记录基线/候选、SLO、p95/p99、错误、饱和、队列、DB/缓存/网络与成本；韧性定义过载保护；文档治理保存实验契约、结果、限制和决策。

**不能接受。** 只报告最高 QPS；使用空数据；只测单服务；不说明资源规格；忽略 tail latency/错误/正确性；把实验室结论直接当作生产容量承诺。

# 重构与演进场景卡

## SC-REF-001：将单体订单模块逐步迁移到新的 Go 服务

**输入。** 老系统使用 Java 单体、共享 MySQL、同步调用；新团队希望用 Go、PostgreSQL、Kafka 重建订单能力，同时保证现有 Web/移动客户端不受影响。

**禁止方案。** 先停工 12 个月重写全部订单；直接让新服务读写所有共享表；没有幂等、对账和回退就双写；为迁移而拆出所有服务。

**必需过程。**

1. 用日志、工单、代码/DB 调查和领域访谈列出订单相关的真实行为、异常和废弃功能；建立成功基线。
2. 选择一个可隔离的能力，例如“订单导出”或“售后状态查询”，通过 façade/API 路由新旧流量。
3. 定义新订单 context 的统一语言、ACL、API/事件、权威数据源和独立 owner。
4. 对需要迁移的数据执行 Expand–Migrate–Validate–Contract；明确每阶段读/写源，执行对账、影子/金丝雀验证。
5. 演练 Kafka 重复/重放、依赖失败、CDC 延迟、数据库恢复、旧客户端与新服务混合版本。
6. 仅在旧路径无依赖、数据不变量验证、观察窗完成并获人工批准后删除旧对象。

**通过条件。** 每一切片都有可见业务收益、可量化风险/性能指标、回退/不可逆点和后续学习，不把过渡层无限期保留。

## SC-REF-002：GORM 引入后查询与迁移问题

**输入。** 团队把手写 SQL 改为 GORM；上线后高峰出现连接耗尽、关联查询变慢、`AutoMigrate` 造成意外 schema 差异。

**通过条件。** 先回收证据：真实 SQL、执行计划、pool 配置、p95/p99、N+1/Preload、事务边界、DDL 差异和流量。明确哪部分维持 GORM、哪部分回到显式 SQL；把 schema migration 迁到可审查/可回退流程；在 staging 用生产近似数据压测和迁移演练；用特征/契约测试确保外部行为不变。

# 领域驱动设计场景卡

## SC-DDD-001：多租户订单与库存预占

**输入。** B2B 客户提交订单；库存来自多个仓库；订单可取消；支付、库存、配送和发票各有独立团队；用户要求实时状态。

**调研问题。** “预占”“可售”“付款成功”“取消”“发货”在各角色中分别是什么意思？哪些体验需要实时，哪些可以异步？超卖、重复提交、支付超时和库存回补的业务规则与可接受时间窗是什么？

**最低交付。**

| 产物 | 必须包含 |
|---|---|
| Context Map | 订单、库存、支付、配送、发票的 owner、模型、数据归属、API/事件与 ACL |
| 状态机 | 订单和库存预占的合法状态/迁移、超时、人工处理和用户可见语义 |
| API 契约 | 提交命令的幂等键、版本/冲突、同步响应与异步进度；查询的 cursor/新鲜度 |
| 事件契约 | `OrderAccepted`、`StockReserved` 等事实事件的版本、key、重放和去重 |
| 质量计划 | 重复命令、并发预占、事件乱序/重放、部分失败、回补与对账 |

**通过条件。** 不存在“订单成功”这种跨域含糊结论；每个状态属于一个明确 owner；前端不通过轮询内部字段猜测最终状态。

## SC-DDD-002：简单 CRM 功能不应被 DDD 过度复杂化

**输入。** 内部后台需要维护客户标签、备注和联系人，单团队、规则少、无独立扩缩需求。

**通过条件。** 采用轻量 Handler/Application/Repository 或模块化单体设计；定义权限、审计、分页、验证和迁移即可。不要求事件总线、多个服务、复杂 aggregate 或 CQRS 双读模型；当规则/协作/规模有证据变化时再重评估。

# 受约束的 Agentic Development Framework

> **结论。** 对小型研发团队，不采用“全流程工具强制每一步”或“AI 自由挑选任何 Agent/Skill”两个极端。采用**确定性框架作为骨架，风险受限的动态编排作为肌肉**：框架负责状态、必需产物、权限、门禁、停止/回退和审计；AI 只能在已授权的节点，从允许的最小角色集合中选择 Skill，并为每次选择留下原因、证据和验证计划。

## 1. 为什么不能让 AI 完全自由发挥

自由编排的优势是能应对跨领域、非标准和探索性问题；但在复杂研发中，AI 容易出现四种不可接受的失败：跳过需求证据就选技术；对不确定事实给出确定结论；选择过多专家造成冲突/成本；在无权或高风险场景执行发布、迁移、权限或外部操作。

流程工具的优势是可重复、可审计和易于培训；但若把每个任务都强制走全量阶段，会产生表单化工作、延迟学习和“按流程通过但不理解问题”的假质量。

因此，**固定“是否可以进入下一阶段”的问题，动态“当前阶段需要谁来完成”**。

## 2. 框架状态机

```text
INTAKE
  → DISCOVERY
  → DECISION
  → BUILD
  → VERIFY
  → RELEASE_READY
  → OBSERVE
  → LEARN / RETIRE

任一阶段：BLOCKED（缺少证据/批准/依赖）
任一高风险动作：AWAITING_HUMAN_APPROVAL
任一验证失败：回到所属阶段，不得静默前进
```

| 状态 | 必需输入 | AI 可动态选择的角色 | 不可跳过门禁 | 允许的最大自主动作 |
|---|---|---|---|---|
| `INTAKE` | 请求、约束、风险初判 | 编排、证据、产品 | 目标/owner/非目标/未知项 | 分类、提出最少澄清、建立 task ledger |
| `DISCOVERY` | 用户/运行证据或明确缺失 | 产品、设计、工程、数据 | 事实/假设分离，研究/POC 计划 | 检索公开资料、整理证据、创建原型/评测计划 |
| `DECISION` | 领域/技术/风险分析 | 架构 + 受影响领域专家 | ADR、Context/API/data 契约、简单替代方案 | 生成方案与 ADR 草案；不批准难逆决定 |
| `BUILD` | 已接受切片和契约 | 后端、前端、数据、平台 | 变更范围、代码/配置审查、无未解释契约漂移 | 在隔离环境实现、运行测试、更新文档 |
| `VERIFY` | 可执行产物 | 质量、韧性、SRE、消费者 | 风险测试、契约/迁移/恢复、残余风险 | 运行测试/静态检查/模拟故障；不篡改生产数据 |
| `RELEASE_READY` | 验证证据、发布契约 | 质量、SRE、产品、架构 | 灰度/停止/回退、owner 批准 | 生成检查清单和发布草案；不自行生产发布 |
| `OBSERVE` | 发布记录、指标、支持/事故信号 | 产品、SRE、质量、架构 | 指标观察窗、异常升级、文档更新 | 汇总指标/告警和提出回退/修复建议 |
| `LEARN / RETIRE` | 复盘、到期/弃用触发 | 证据、所有者、相关角色 | 行动项、ADR/Runbook/知识卡更新 | 创建修订/退役提案，保持历史可追溯 |

## 3. 风险分级与权限模型

| 级别 | 示例 | AI 自主范围 | 必须的人类门禁 |
|---|---|---|---|
| R0：研究/草案 | 公开资料研究、文档草稿、局部设计、测试计划 | 可自主生成与核验来源 | 无，但需标注不确定性 |
| R1：可逆隔离变更 | 本地代码、测试、模拟/开发环境、低影响重构 | 可执行受限变更/测试；提交建议 | 代码/领域 owner review 后合并 |
| R2：共享/兼容影响 | API、schema、共享库、权限模型、CI/CD | 仅生成计划/变更集和验证证据 | 架构/消费者/数据/质量 owner 批准 |
| R3：生产或难逆影响 | 发布、数据回填/删除、K8s 权限/网络、成本承诺、外部通信 | 不自主执行；只能提出操作和检查清单 | 明确人类批准、双人复核或既定 runbook 执行者 |

**即使用户给出广泛默认授权，R2/R3 的行动仍保留人工 owner 门禁。** 授权可以减少反复确认，但不能把不知道的业务优先级、数据影响或外部后果交给模型猜测。

## 4. 动态编排契约

AI 在每个状态输出一份小型、可审计的路由记录。它不应“叫来所有 Skill”；只选择覆盖当前风险的最少角色。

```yaml
routing_record:
  task_id: ""
  framework_state: "DISCOVERY | DECISION | BUILD | VERIFY | RELEASE_READY"
  risk_tier: "R0 | R1 | R2 | R3"
  facts: []
  assumptions_and_unknowns: []
  required_artifacts: []
  selected_roles:
    - role: ""
      question_owned: ""
      evidence_or_input: []
      expected_handoff: ""
      why_required_now: ""
  deliberately_not_selected: []
  allowed_actions: []
  blocked_actions_and_human_approvals: []
  validation_and_stop_conditions: []
  audit_links: []
```

### 4.1 选择规则

| 触发信号 | 必选角色 | 可选角色 | 不允许的捷径 |
|---|---|---|---|
| 用户问题/范围不清 | 产品发现 | 前端设计、架构 | 直接进入技术选型 |
| 核心规则/多团队术语/数据 owner 不清 | 架构 | 后端、数据、产品 | 按表或技术层命名服务 |
| HTTP/API/事件/SDK 变化 | 后端 + 前端/消费者 + 质量 | 架构、数据、韧性 | 只改后端而不做契约/兼容检查 |
| 并发、超时、依赖、容量 | 韧性 + SRE + 后端 | 数据、架构 | 仅添加 retry 或熔断配置 |
| 数据/迁移 | 数据 + 后端 + 质量 | SRE、架构 | 只看 ORM migration 成功 |
| 生产事故 | SRE 指挥/操作/沟通角色 | 后端、数据、质量、架构 | 多 Agent 自由修改系统 |
| 重构/遗留替换 | 架构 + 质量 + 受影响 owner | 数据、SRE、产品 | 大爆炸重写或无行为基线迁移 |
| 私有书籍/复盘/ADR 的知识沉淀 | Distilly → 技术蒸馏 → 证据审校 | 对应领域 | 将 Distilly 输出当成无条件事实 |

## 5. 防止 AI “瞎搞”的具体控制

1. **事实、假设、建议三分。** 不允许混写；无证据的内容必须为 `unknown` 或带验证任务。
2. **产物门禁而非语言门禁。** 不是要求 AI 说“已考虑安全”，而是要求具体 ADR、契约、测试、指标、runbook、批准记录。
3. **最小委派。** 编排器记录为什么选/不选每个角色；超过风险需要的并行角色必须说明收益。
4. **有限预算。** 每个阶段限制轮次、工具权限、文件范围和时间；达到上限转人类或降级为草案。
5. **独立验证。** 实现者不得独自批准高风险实现；质量/证据/消费者或 owner 负责挑战。
6. **可复现与可回退。** 所有变更有工作树/分支、测试命令、输入/输出、环境、回滚路径；不得依赖未记录的聊天上下文。
7. **行动分离。** AI 可以计划、写草案、在隔离环境验证；生产、外部发布、权限、支付、删除/迁移由人类批准和受控执行。
8. **观察后才结案。** 发布/变更后按预先定义的业务和技术信号观察，失败则进入恢复/学习，不把“命令执行成功”当作结果成功。

## 6. 团队的推荐运行方式

**开发框架作为项目级控制面。** 将状态机、风险等级、产物模板、审批人、知识包路径、文档 DoD、测试/发布门禁固化在仓库中。它决定“什么必须存在”和“什么绝不能自动做”。

**Skill/Agent 作为任务级执行面。** 编排器依据任务状态与风险，调用产品、架构、后端、前端、数据、SRE、韧性、质量、证据和 Distilly；每个角色只处理有界问题，并用 handoff contract 返回结果。它决定“谁最适合完成这个问题”。

**人作为业务/风险控制面。** 人类 owner 决定价值优先级、不可逆取舍、生产操作、数据/隐私/成本影响和冲突裁决；AI 提升分析、草案、验证和可追溯性，但不替代责任主体。

## 7. 最小落地顺序

1. 先把 `routing_record`、ADR、API/事件契约、迁移 charter、release contract 和 runbook 模板加入仓库。
2. 启用 R0/R1：让 AI 负责文档草案、资料检索、代码/测试建议和隔离环境验证；记录实际错漏。
3. 再启用 R2：在人工评审下处理契约/共享变更，审查生成的 routing record 与门禁遗漏。
4. R3 仅让 AI 生成检查清单和证据包，保留人工执行；只有在特定、可审计、可回退的 runbook 中才逐步授权。
5. 每月从事故、返工、被拒绝变更和文档陈旧事件中更新路由规则与知识卡。

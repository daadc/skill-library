# Redis 知识卡

## KC-RDS-001：Redis 缓存如何避免成为数据一致性隐患？

**问题。** 何时把 Redis 当缓存，如何定义读写、失效、穿透和故障降级行为？

**原则。** 先定义权威数据源和允许陈旧度，再选择缓存模式。Redis 缓存不自动解决数据库与缓存之间的失效、并发写入、热点、雪崩或恢复一致性问题；这些都必须由应用协议、过期策略、容量与可观测性共同处理。

**最低缓存契约。**

| 维度 | 需要明确的内容 |
|---|---|
| 权威源 | 哪个系统对数据写入和最终值负责？ |
| 一致性 | 允许的最大陈旧度、写后读要求、失效优先级 |
| 键设计 | 命名空间、租户隔离、版本、TTL、最大值大小与基数预估 |
| 失效 | 删除、更新、短 TTL、事件驱动或组合策略；失败时怎么处理 |
| 保护 | 穿透、击穿、雪崩、热键和单租户放大的降级与限流 |
| 可观测性 | 命中率、延迟、错误、驱逐、内存碎片、热键、连接与命令分布 |

**验证。** 在数据库慢、缓存空、缓存连接中断、并发失效和热点突发下验证用户可见行为与后端负载；不得只以“命中率高”证明设计正确。

## KC-RDS-002：如何选择 RDB、AOF 或组合持久化？

**问题。** Redis 承载重要数据时，如何从“能落盘”升级为可恢复性设计？

**原则。** RDB 是按时点生成的紧凑快照，便于备份和较快重启，但故障时可能丢失两个快照之间的数据；AOF 记录写操作，持久性取决于 fsync 策略，体积和运行代价也不同。Redis 官方资料建议在需要较强数据安全时考虑组合使用，并明确备份与恢复流程。[1]

**决策表。**

| 场景 | 倾向 | 必须补充 |
|---|---|---|
| 可安全重建的缓存 | 可不持久化或以轻量快照为主 | 重建流量和后端保护方案 |
| 允许分钟级数据损失 | RDB 可能可接受 | 快照频率、跨机/跨地域备份和恢复演练 |
| 需要较低 RPO | AOF `everysec` 或组合方案 | 可接受的一秒级风险、磁盘延迟和 rewrite 影响 |
| 关键业务状态 | 不要只以 Redis 持久化代替完整系统设计 | RPO/RTO、外部备份、恢复演练与权威数据边界 |

**风险。** 任何 `fork()` 型持久化或 rewrite 都受数据规模、写入量、内存 copy-on-write 与磁盘 I/O 影响。AOF 备份在 rewrite 期间需要遵守版本对应的安全流程；“有备份”不等于“可恢复”。[1]

**验证。** 定期在隔离环境恢复备份，核验键数量、关键样本、数据时间点和恢复耗时；为持续写入和 rewrite 做容量压测。

## KC-RDS-003：复制、Sentinel 和 Cluster 分别解决什么问题？

**问题。** 如何避免把“有副本”误认为没有数据丢失、没有故障窗口？

**原则。** Redis 复制通常是异步的；Sentinel 在非 Cluster 部署中提供监控、通知和自动故障转移能力；Cluster 还处理分片和集群级可用性。选择必须从数据分片需求、RPO/RTO、客户端拓扑感知、跨可用区故障和运维能力出发，而非只看节点数量。[2] [3]

**设计检查。**

1. 明确主写、读副本、读陈旧度和故障转移期间的应用重试/降级行为。
2. 明确 Sentinel/Cluster 客户端发现、DNS/网络、认证、TLS 和连接池的运行方式。
3. 为复制延迟、全量同步、故障转移、脑裂/网络分区和副本重建建立告警与演练。
4. 如果需要横向容量或分片，评估 Cluster 的键分布、跨槽操作限制和客户端兼容性。
5. 任何切换前后都验证写入确认、关键读取、复制健康和备份恢复。

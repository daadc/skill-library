# 架构演进与成熟案例知识卡

> **举一反三的原则。** 优秀案例不是复制对象。应提取其触发条件、约束、边界、风险和验证方法，再与自己的团队规模、领域复杂度、可靠性目标、资金和运维能力相匹配。

## KC-ARC-001：默认从“模块化单体”起步，而非默认微服务

**问题。** 新团队是否应一开始就拆成多个服务？

**原则。** Shopify 的公开案例表明，单体在早期有部署、搜索、测试、数据访问和基础设施成本较低的优势；当高耦合、跨域影响、慢 CI、困难测试和新成员需要理解过多上下文等问题有证据地成为瓶颈时，可先演进为模块化单体：仍以单一应用部署，但用严格的业务域边界、公开接口、数据所有权和自动检查降低耦合。[1]

| 信号 | 优先动作 | 不应立刻得出的结论 |
|---|---|---|
| 功能仍少、团队小、领域未稳定 | 单体 + 模块边界 + 自动测试/发布 | “未来会大，所以现在拆微服务” |
| 模块随意跨域调用/直接读写对方数据 | 定义领域 API、归属、依赖规则并在 CI 检查 | “换仓库/加网络调用就自动解耦” |
| 独立扩缩/独立发布/可靠性需求已被测量证明 | 评估抽取特定边界 | “所有模块都应同时拆出” |
| 跨团队频繁互相阻塞 | 优化领域边界、所有权和接口 | “多服务能解决所有协作问题” |

**最小边界契约。**

```yaml
module_contract:
  domain: "订单/库存/计费等业务概念"
  owner: "负责团队"
  public_api_or_events: []
  owned_data: []
  allowed_dependencies: []
  forbidden_access: ["跨模块表/集合直读", "隐式全局状态"]
  compatibility: "调用/数据版本策略"
  boundary_tests: []
```

## KC-ARC-002：微服务拆分要以业务功能、独立演进和迁移证据为中心

**问题。** 什么条件下微服务的分布式成本值得付？

**原则。** Netflix 的视频处理案例将既有系统中难以独立演进、共同发布、业务功能耦合和长发布周期作为重构动机；其服务边界来自处理步骤和业务功能，复杂业务流程通过专用编排服务适配不同用例，并在生产中逐步迁移流量。[2]

**拆分前证据表。**

1. 哪个业务能力有独立变化节奏、所有者、SLO、容量或安全边界？
2. 当前共同发布/测试/容量耦合的成本是多少，有哪些真实例子？
3. 数据所有权、API/事件契约、幂等、可观测性、权限和故障语义能否明确？
4. 新服务的 CI/CD、告警、runbook、容量、成本和 on-call 由谁承担？
5. 能否以 strangler、旁路写、影子流量、双读或逐用例迁移控制风险？

**反模式。** 仅按技术层（controller/service/repository）拆服务；为了“云原生”增加同步 RPC 链；共享一个数据库却假装服务独立；没有回退、可观测性和数据兼容计划就切换全部流量。

## KC-ARC-003：用单元化/Cell 架构限制租户和区域的爆炸半径

**问题。** 多租户系统如何避免单租户、单个部署或单个区域问题影响所有客户？

**原则。** AWS 将 cell-based architecture 描述为把可用区/区域等故障隔离思想扩展到工作负载架构，以取得更强的故障隔离、可预测性和可测试性。它更适合关键性高、规模大或需要强租户隔离的系统，不是低复杂度产品的默认选择。[3]

| 设计问题 | 单元化回答 |
|---|---|
| 路由 | 用户/租户/数据按什么稳定规则落到 cell？故障时如何避免全局重平衡风暴？ |
| 状态 | 哪些数据局部于 cell，哪些是全局控制面？控制面故障如何处理？ |
| 容量 | 每个 cell 的峰值、余量、扩容速度和租户热点策略？ |
| 发布 | 能否先在一个 cell 金丝雀，再按 cell 推进并保留回退？ |
| 运行 | cell 级 SLO、告警、演练、隔离和故障注入如何做？ |
| 成本 | 复制基础设施与运维复杂度是否被风险收益证明？ |

**验证。** 模拟单 cell 过载、故障、升级失败、依赖不可用和租户洪峰；证明其他 cell 的 SLO、数据边界和恢复流程不受不可接受影响。

## KC-ARC-004：架构演进的共同模式是“小步、可观测、可逆”

**问题。** 如何从成熟案例里抽取适用于小团队的实践？

**可迁移模式。**

| 模式 | 从案例中抽取的做法 | 小团队的简化实施 |
|---|---|---|
| 先测量痛点 | Shopify 先收集开发者痛点和边界违规；Netflix 指出共同发布/长周期 | 记录 lead time、失败率、跨模块 PR、CI 时长和事故；不要靠潮流拆分 |
| 明确领域边界 | Shopify 以业务概念组织和接口隔离；Netflix 按处理功能划服务 | 写模块/服务契约，禁止跨域直读，先在 CI 进行结构检查 |
| 控制爆炸半径 | AWS 用 cell 限制影响范围 | 从 feature flag、租户限额、独立队列/池、namespace 开始，而非立刻多区域 cell |
| 渐进迁移 | Netflix 并行运行并逐用例切流 | 使用旁路、影子读、双写前的对账、金丝雀和停机条件 |
| 平台能力复用 | Netflix 用工作流与通用抽象让领域团队专注 | 先提供模板化 CI、部署、观测和 runbook，避免每个服务自造平台 |

**结论。** 架构的成功不在于采用“单体”或“微服务”标签，而在于边界是否反映真实领域，变更是否能够独立验证和回退，故障是否被局部化，团队是否承担得起新增运维复杂度。

# 架构演进场景卡

## SC-ARC-001：是否应把订单模块拆成微服务？

**输入。** 订单、库存和促销在单一仓库和数据库中；团队抱怨改动互相影响、CI 变慢，并计划拆成三个服务。

**责任路由。** `tech-lead-architect` 主持；`backend-runtime-engineer`、`data-engineer`、`platform-sre-engineer`、`quality-engineer` 参与；`product-discovery-manager` 确认独立交付价值。

**必需证据。** 变更前置时间、CI/测试耗时、跨域依赖、数据归属、独立扩缩/发布需求、失败模式、运行成本、可迁移的第一条业务路径。

**通过条件。** 至少比较三种选择：维持现状、模块化单体、抽取一个有明确所有权的服务。若选择拆分，交付边界契约、数据/API/事件兼容、观测、迁移/回退和分批切流计划。

## SC-ARC-002：单租户流量洪峰是否需要 cell？

**输入。** 最大租户的季度任务会使所有客户 API 延迟上升。团队提议建设多区域 cell。

**通过条件。** 先比较限流、队列隔离、独立 worker、资源配额、缓存分片、tenant partition 与 cell 的复杂度/收益。只有在隔离目标、容量、路由、状态边界、发布与演练能力明确时，才进入 cell 方案；不以“更像大厂”作为理由。

## SC-ARC-003：重构视频/文件异步处理管道

**输入。** 管道包含上传、扫描、转码、分析、通知和归档；当前全部任务随单体版本共同发布，任何模块升级都会拖慢整个发布。

**通过条件。** 识别独立业务功能和不同延迟/可靠性需求；定义工作流编排与服务边界；采用旁路或逐用例切流；验证幂等、积压、回放、成本、回滚和用户状态语义。参见 KC-ARC-002。

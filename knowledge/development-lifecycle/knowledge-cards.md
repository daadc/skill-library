# 标准研发流程知识卡

> **工作流优先于仪式。** 标准流程的目的不是增加会议或模板，而是在不可逆、跨团队或高影响的决策之前，让合适的人基于可验证证据做出可回滚的选择。

## KC-SDLC-001：一个完整变更应经过哪些阶段？

**问题。** 如何让产品、研发、测试、SRE 和数据角色对“完成”达成一致？

**原则。** 变更从问题与用户价值开始，经过可验证的设计、实现、审查、测试、发布、运行观测和学习闭环。发布工程应从产品周期开始设计，而不是在临近上线时补上；代码评审要同时检查设计、功能、复杂度、测试和文档。[1] [2] [3]

| 阶段 | 核心问题 | 必备产物 | 退出条件 |
|---|---|---|---|
| 发现 | 谁的问题？价值、风险、非目标是什么？ | 问题陈述、指标基线、范围、验收标准 | 产品与技术均理解成功与失败 |
| 设计 | 哪些边界、数据、失败模式、替代方案？ | ADR、接口/事件契约、风险评估、发布/回滚草案 | 不确定假设有验证计划 |
| 实现 | 怎样保持变更小、可审查、可构建？ | 小批量提交、不可变构建标识、迁移脚本 | 本地/CI 构建可重复 |
| 评审 | 是否提升整体代码健康而非追求无关完美？ | 评审记录、测试/文档变更 | 设计、功能、复杂度、测试等风险被处理 |
| 验证 | 真实失败下是否仍符合契约？ | 单元、集成、契约、端到端、性能/安全或故障测试 | 覆盖与风险成比例，关键路径可复现 |
| 发布 | 如何限制爆炸半径并快速停止？ | 版本、配置、金丝雀、指标、停机条件、回滚 | 产物、配置、审批和观察窗口可追溯 |
| 运行与学习 | 是否兑现 SLO，如何把事故转成改进？ | SLI/SLO、告警、复盘、行动项 | 行动项有负责人、截止和验证证据 |

**边界。** 低风险文案或可逆 UI 调整不需要同等重量的 ADR；数据迁移、权限、结算、集群升级和外部行为变更则应加强门禁。

## KC-SDLC-002：如何做有效而不阻塞的代码评审？

**问题。** 如何避免评审既沦为格式检查，又成为长时间阻塞？

**原则。** Google 的公开工程实践把代码评审看作日常开发流程，审查设计、功能、复杂度、测试、命名、注释、风格和文档。评审标准是“整体代码健康明确改善”，而不是使每个改动达到抽象的完美状态。[1] [2]

**评审序列。**

1. 作者先让变更小且单一目的，附上问题、范围、风险、测试、截图/指标和回滚说明。
2. 评审者先判断产品/系统设计，再判断边界、错误处理、并发/资源、数据兼容与测试；最后才是命名和格式。
3. 将 **必须修改** 与可选的 `Nit` 清晰分开；以数据、现有约定或工程原则替代个人偏好。
4. 高风险变更需要独立角色复核：数据/迁移由 `data-engineer`，发布/容量由 `platform-sre-engineer`，安全或外部事实由 `evidence-safety-auditor`。
5. 争议无法通过证据解决时，快速升级给技术负责人，并将决策记录在评审或 ADR 中。

**反模式。** 大型混合 PR、只看代码不看可观测性、用“测试覆盖率”代替风险测试、让实现者批准自己的高风险变更、让评审无限等待。

## KC-SDLC-003：如何设计“可发布”而非仅“可合并”的变更？

**问题。** 为什么 CI 通过仍不足以安全上线？

**原则。** 可发布变更需要可重复构建、可追溯版本与配置、面向实际发布产物的测试、按风险选择的渐进发布和可操作回滚。Google SRE 强调密封构建、持续测试与发布审计；发布速度和稳定性应一起观察。[3] [4]

```yaml
release_contract:
  change_id: ""
  artifact: "不可变版本或摘要"
  config_version: "与产物的兼容关系"
  dependencies: []
  database_or_event_contract: "前向/后向兼容性与恢复点"
  rollout: "范围、批次、观察窗口"
  success_signals: ["业务成功率", "错误率", "延迟", "饱和度"]
  stop_conditions: []
  rollback: "谁、何时、如何回滚；哪些状态不能仅靠镜像回退"
  approval: "按风险需要的人工批准"
```

**度量。** DORA 当前将交付表现分为吞吐（变更前置时间、部署频率、失败部署恢复时间）与不稳定性（变更失败率、部署返工率）。这些指标应按应用/服务的上下文观察趋势和瓶颈，不能作为个人绩效竞赛或跨系统排名。[4]

## KC-SDLC-004：如何把“架构”与“需求/实现”连成闭环？

**问题。** 如何避免 ADR 是独立文档、PRD 是独立文档、代码又是另一套真相？

**原则。** 每个会影响模块边界、数据所有权、外部契约、成本、可靠性或长期可维护性的决策，都应从用户目标倒推技术选择并连接到验收和运行指标。

**最小 ADR。**

| 字段 | 内容 |
|---|---|
| Context | 用户/业务目标、约束、现有事实与未知项 |
| Decision | 选择了什么、未选择什么、谁负责 |
| Consequences | 正面收益、复杂性、成本、风险、迁移影响 |
| Contracts | API、事件、数据、超时/重试、权限与版本兼容性 |
| Delivery | 分批策略、观测、停止/回滚条件、审批 |
| Evidence | 原型、压测、客户研究、运行数据或权威来源 |

**验证。** 每次重大变更在上线后回看 ADR 中的假设与真实指标；若假设错误，修正决策记录和知识卡，而不是只修代码。

# MongoDB 知识卡

## KC-MDB-001：如何从访问模式设计 MongoDB 文档和索引？

**问题。** 如何避免用关系数据库表结构的直觉直接堆叠 MongoDB collection？

**原则。** 文档边界应该由读取/写入原子性、增长模式、查询路径、关联生命周期和数据分布决定。先写清业务不变量、常见查询与更新，再决定嵌入、引用、索引和分区方式；模型不是为了“少 collection”或“少 join”而优化。

**设计步骤。**

1. 写出实体、不可变标识、生命周期、大小增长、保留期和敏感字段。
2. 收集实际查询：过滤、排序、分页、聚合、更新频率和预期基数。
3. 根据需要的单文档原子性、读写局部性和无界增长风险决定嵌入或引用。
4. 为查询设计索引，并用真实数据分布与执行计划验证；评估索引对写入、存储和内存的成本。
5. 定义 schema 演进、数据回填、兼容窗口和回滚策略。

**验证。** 以代表性数据做查询性能、热点写入、文档增长、索引构建和迁移演练；不得只以小样本/空数据库结果下结论。

## KC-MDB-002：复制集读写关注点如何影响应用语义？

**问题。** 如何在高可用、读扩展和一致性之间明确应用可见行为？

**原则。** Replica set 由一个 primary 和多个 secondary 组成；secondary 异步复制 primary 的 oplog。primary 默认接收写入，而读取偏好、read concern 和 write concern 会决定陈旧读取、确认时机和故障转移期间的表现。[1]

| 选择 | 适用思路 | 必须声明的代价 |
|---|---|---|
| Primary read | 读后写一致性或强业务正确性优先 | 主节点读压力与故障窗口 |
| Secondary read | 可容忍陈旧数据的读扩展/报表 | 复制延迟、拓扑变化和路由行为 |
| `w: "majority"` | 需要较强写入确认语义 | 延迟、可用副本要求与故障策略 |
| `local/available` 读取 | 可接受回滚/陈旧风险的场景 | 可能读到后来被回滚的结果 |

**故障转移要求。** 应用驱动、连接池和重试逻辑必须针对选主与短暂 primary 不可用设计；降低选举超时可能加快故障检测，却增加网络抖动时不必要选举和 `w:1` 写回滚风险。[1]

**验证。** 演练 primary 故障、网络分区、secondary lag 和负载切换，验证用户级语义而非仅检查节点状态。

## KC-MDB-003：何时引入分片与多文档事务？

**问题。** 如何避免把分片和事务当成默认架构组件？

**原则。** 分片用于把大数据集和高吞吐分布到多台机器，但增加分片键、数据分布、查询路由、再平衡和运维复杂度。多文档事务可提供跨文档原子性，但应从真实不变量出发，并评估延迟、竞争、重试和跨分片成本。[2] [3]

**决策门。**

1. 单副本集的垂直资源、索引、查询、归档与数据模型优化是否已测量到边界？
2. 分片键能否支撑高基数、写入分散、目标查询和长期增长，避免热点？
3. 跨文档不变量能否通过重构文档边界、幂等工作流或补偿方式满足？
4. 引入事务后是否仍能在目标并发和故障条件下满足 SLO？
5. 是否已定义监控、备份恢复、balancer 行为和跨区域/租户边界？
